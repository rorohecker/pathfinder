# Pathfinder audit and proposed plan

Date: 2026-09-28. Checkout: pathfinder v1.0.22, including the uncommitted search-help changes from this conversation.

Analysis only. No application fixes were made for this audit.

The first priority is data safety and consistent file identity, followed by search correctness. Performance work should reduce unnecessary work before adding more parallelism.

This is a broad static audit with targeted, read-only verification, not a claim that every possible bug has been found. I traced the principal operations, search, navigation, UI, indexing, AI, caching, and Windows integration paths. I did not run destructive operations, hardware inference, installer upgrades, screen-reader sessions, or representative performance benchmarks.

The earlier cargo check and strict Clippy runs passed. They establish compilation/lint health, not behavioral correctness. The source contains 55 test annotations; the interactions below need additional coverage.

Evidence labels: **confirmed** means established by code, not necessarily reproduced on real files; **reproduced** means an isolated non-writing probe demonstrated it; **risk** needs controlled runtime confirmation; **performance target** identifies unnecessary work without claiming measured latency; **UX gap** needs interaction/accessibility validation. P1 means data safety, incorrect targeting/results, broken functionality, or major freezes; P2 means substantial reliability/performance/usability work; P3 means polish.

The main Rust module is 31,409 lines. Its concentration of responsibilities contributes to inconsistent policy across entry points. Extract modules after defining invariants and tests; splitting files alone will not fix these behaviors. Source references below use line numbers from this audit snapshot.

## Data safety and operations

### 1. Sorting can change the selected files — P1, confirmed

**Evidence:** [lib.rs:20209](../src-tauri/src/lib.rs#L20209) (primary sort), 20957 (secondary sort), 15687 (selection resolution). Selection is stored as row indices; sorting reorders files without restoring selection by identity. Select a file, change sorting, then Delete/Rename: the index can target a different file.

**Fix plan:** store selected IDs, focused ID, and range anchor independently of row order. As an initial fix, reuse the existing path-preserving helpers around every reorder. **Validate:** every sort column/direction in both panes preserves the exact command-target set.

### 2. Right-pane commands can act on left-pane files — P1, confirmed

**Evidence:** [lib.rs:26373](../src-tauri/src/lib.rs#L26373) (diff), 26417 (batch tags), 26434 (batch notes). These obtain active-pane indices but resolve them against primary visible_files. The existing selected_entries/selected_paths helpers use the correct pane.

**Fix plan:** selected-file commands consume resolved entries/paths from one pane-aware service, never unqualified indices. **Validate:** put unrelated files at matching row positions in both panes; only the selected right-pane paths may change.

### 3. Redo-delete bypasses the Recycle Bin — P1, confirmed

**Evidence:** [lib.rs:26216](../src-tauri/src/lib.rs#L26216). Redo calls permanent native_delete_path first, falling back to trash only on failure. Delete → Undo → Redo therefore changes ordinary delete into permanent deletion.

**Fix plan:** record deletion mode and replay it faithfully; capture a fresh trash identity for each recycled deletion. **Validate:** Delete → Undo → Redo → Undo remains recoverable; permanent deletion remains a separate explicit action.

### 4. Undo/redo history records its own inverses and loses failed entries — P1, confirmed

**Evidence:** [lib.rs:26100](../src-tauri/src/lib.rs#L26100), 12773, 21791. Undo calls normal logging operations; batch rename logs individual changes plus an aggregate. Entries are popped before success and not restored after failure. Redo invokes logging operations and then pushes the original record again. The only explicit redo-stack clear found is Clear History, leaving stale branches after new actions.

**Fix plan:** separate execution from history recording; one transaction per user action, non-recording replay, and commit history transitions only after success. Preserve partial recovery details and invalidate redo after new actions. **Validate:** multi-step undo/redo, batch failure, destination changes, and new actions after undo.

### 5. Redo-copy has different overwrite and directory semantics — P1, confirmed

**Evidence:** [lib.rs:26212](../src-tauri/src/lib.rs#L26212) uses fs::copy directly. Folder copies cannot replay correctly, and newly recreated destination files can be overwritten without the normal conflict decision.

**Fix plan:** replay through the same validated operation engine with recorded destinations and preconditions. **Validate:** folder redo, externally modified destination, and conflict parity with the original copy.

### 6. Replace destroys the old destination before success — P1, confirmed

**Evidence:** [lib.rs:2131](../src-tauri/src/lib.rs#L2131), 23785, 22903, 7333. Rename, paste, remembered replacement, and ZIP extraction remove the destination before the replacement completes. Missing sources, full disks, permission errors, or corrupt archives can leave neither the old data nor a valid replacement. Remembered paste replacement even deletes during preflight.

**Fix plan:** stage beside the target, verify, retain a recoverable old version, and atomically replace where supported. Preflight must never mutate data. Folder replacement needs a reviewed merge plan. **Validate:** failures at every stage leave the old destination recoverable.

### 7. Paste can recursively copy a folder into its descendant — P1, confirmed

**Evidence:** [lib.rs:1656](../src-tauri/src/lib.rs#L1656), 16855, 22742. Drag checks canonical ancestry; paste only handles same-path cases. Recursive copy creates the output before walking the source, so a descendant output can become new input.

**Fix plan:** source/destination identity and ancestry checks inside the shared operation engine, before any creation, including case, UNC, aliases, and reparse points. **Validate:** descendant paste, same-folder duplication, cross-volume moves, and drag/clipboard parity.

### 8. Windows archive containment needs stronger validation — P1, risk

**Evidence:** [lib.rs:7287](../src-tauri/src/lib.rs#L7287) rejects absolute paths and parent components, then joins the name. Rooted-but-not-fully-absolute and drive-relative Windows forms need explicit rejection. Existing destination junctions can also escape lexical checks. Rejected entries are silently skipped.

**Fix plan:** accept only safe normal relative components; reject root/prefix/alternate-stream forms as appropriate; verify containment through existing ancestors and avoid unexpected reparse points. Report rejected entries. **Validate:** a disposable malicious-path corpus and destination junction; no writes outside the extraction root.

### 9. Persistence can lose state on crashes or racing writes — P1, risk

**Evidence:** [lib.rs:11084](../src-tauri/src/lib.rs#L11084), 14397. JSON writes truncate destinations directly; invalid reads silently use defaults. The writer drains its queue before writing, so shutdown flush cannot wait for already-drained work. Multiple windows also write common files without coordination.

**Fix plan:** serialized persistence, temp/flush/replace plus backup, a shutdown acknowledgement barrier, and revision/conflict handling across processes. **Validate:** crash mid-save, immediate quit, disk-write failures, corrupt primary files, and two-window tag/settings edits.

### 10. Registry cleanup can remove another app's registration — P1, risk

**Evidence:** [folder_shell_registry.rs:178](../src-tauri/src/folder_shell_registry.rs#L178), 234, 300. Registration overwrites values without preserving previous ownership; reset/uninstall deletes trees without checking whether they still point to Pathfinder.

**Fix plan:** snapshot previous values, restore only values still owned by this installation, and preserve unrelated values/subkeys. **Validate:** configure another file manager after Pathfinder, then uninstall Pathfinder; the later registration survives.

## Search correctness and index integrity

### 11. Search providers do not enforce the same query — P1, confirmed

**Evidence:** [lib.rs:4376](../src-tauri/src/lib.rs#L4376), 4408, 9684, 9726, 20095, 28812. Windows Search strips colon-bearing tokens and builds name predicates. FTS retrieval does not enforce every parsed kind/size/date/content constraint. The SQLite fallback combines broad name/path clauses with extension matching using OR. Merged results reach the UI without a final shared predicate check.

**Impact:** a query such as “report size:>10mb” can return different, nonconforming results depending on the provider. Extra tokens in the search-help panel promise behavior the backend does not consistently deliver.

**Fix plan:** parse once into a typed query; give each provider an explicit capability contract; apply shared predicates to constraints it cannot push down. Apply result limits after filtering, or fetch further candidates. Content constraints must mean verified content matches, not silently degrade to name matches. **Validate:** one reference result set for each query across providers individually and combined, including quoted phrases, extension, date, size, tags, and content.

### 12. SQL path scope can exclude children or include siblings — P1, reproduced

**Evidence:** [lib.rs:9689](../src-tauri/src/lib.rs#L9689), 9739, 9418, 11391. Scope predicates use inconsistent LIKE escaping and omit a directory boundary in some paths. An isolated in-memory SQLite probe reproduced both problems: an unescaped Windows path with an ESCAPE backslash fails to match an ordinary child; an escaped “Docs%” prefix also matches “DocsOld”. The fallback's broad name clause also allows a non-PDF through an extension-only query.

**Fix plan:** one normalized scope helper with explicit exact-directory/descendant semantics, correct wildcard escaping, and a separator boundary. Prefer indexed normalized parent/root fields where appropriate. **Validate:** drive roots, trailing separators, UNC paths, case differences, percent/underscore characters, and adjacent names such as Docs and DocsOld. The probe did not touch application data.

### 13. Partial indexing batches are treated as complete directory snapshots — P1, confirmed

**Evidence:** [lib.rs:11022](../src-tauri/src/lib.rs#L11022)–11053 and 9247–9273. The broad indexer flushes parent-grouped entries when its map grows beyond 128 parents. The directory indexing function reconciles each supplied group as a complete directory and deletes missing rows, including associated FTS/embedding/hash data. Traversal can split one parent's children across flushes.

**Impact:** indexing more of the tree can remove previously indexed siblings. Search coverage and cached AI/image work become unstable.

**Fix plan:** separate incremental upserts from complete-directory reconciliation. Prune only after a directory scan completes successfully, using a scan generation or explicit completion event. Never prune after cancellation or access failure. **Validate:** deep and wide trees crossing the batch threshold; index contents must equal a reference traversal after every complete scan.

### 14. Folder filters and refreshes can replace a deep-search result set — P1, confirmed

**Evidence:** [lib.rs:15817](../src-tauri/src/lib.rs#L15817), 20975, 28812. Filter setters rebuild from the current directory's files, while asynchronous search results assign their own entries without consistently composing those filters.

**Impact:** a filter can unexpectedly collapse a recursive search to the current directory, and a later result batch can undo the visible filter.

**Fix plan:** make the current result source explicit: directory listing, search session, or collection. Derive the visible list through a shared filter/sort/selection pipeline; refresh the active source. **Validate:** toggle filters during streaming search, then sort, refresh, switch panes/tabs, and navigate back.

### 15. Tag search is global and does not compose reliably — P2, confirmed

**Evidence:** [lib.rs:15799](../src-tauri/src/lib.rs#L15799), 15864, 19915. Tag lookup traverses global metadata without a directory scope. Special-case parsing consumes the remainder after a tag prefix, and tag handling can short-circuit general search.

**Fix plan:** represent tags as normal query predicates with stable tag IDs. Distinguish an explicitly global tag collection from a scoped folder search in the UI. **Validate:** the same tag on multiple drives; combined tag/name/type/date queries; renamed tags and unavailable paths.

### 16. Watcher eviction and pause/resume can leave stale listings — P2, confirmed/risk

**Evidence:** [lib.rs:5288](../src-tauri/src/lib.rs#L5288), 5334, 23834, 23851. The bounded watcher map evicts arbitrary HashMap keys rather than least-recently-used entries, without reliably pinning active views. Pausing destroys watchers; resuming reattaches them without reconciling changes made while paused.

**Fix plan:** pin active pane paths, maintain actual recency for optional watchers, and rescan after resume or overflow. Coalesce change bursts into targeted directory reconciliations. **Validate:** external edits while minimized/paused and navigation through more than eight watched locations, including both panes.

## Performance, cancellation, and resource budgets

### 17. Duplicate detection can block the UI thread — P1, confirmed

**Evidence:** [lib.rs:23110](../src-tauri/src/lib.rs#L23110), 23171. Duplicate commands synchronously invoke duplicate discovery from UI callbacks. Parallel hashing inside the routine does not release the UI callback while it waits.

**Fix plan:** run discovery in a bounded worker service with cancellation, generation IDs, and progressive group delivery. Keep view-model mutation on the UI thread. **Validate:** interaction and cancellation latency on a large mixed-size corpus, including a slow drive and unreadable files.

### 18. Storage analysis always starts an extra duplicate scan — P2, confirmed

**Evidence:** [lib.rs:6717](../src-tauri/src/lib.rs#L6717)–6733. After marking storage analysis done, the worker starts duplicate discovery unless cancellation was already requested. Cancellation is not carried through that hashing pass.

**Fix plan:** publish storage totals independently. Make duplicate analysis an explicit optional phase, reuse already collected size buckets, and pass cancellation through reads and hashes. **Validate:** requesting storage totals alone performs no duplicate hashing; cancelling either phase promptly stops its work.

### 19. Similar-image grouping is quadratic and order-dependent — P2, confirmed

**Evidence:** [lib.rs:11391](../src-tauri/src/lib.rs#L11391), 11418. The routine loads hashes and compares candidates in nested loops, using seen flags and representative-based grouping. Ten thousand images can require roughly 50 million pair comparisons; that is an operation count, not a measured time.

**Fix plan:** define whether a group means connected similarity or similarity to a representative. Use a Hamming-distance candidate structure such as a BK-tree or multi-index buckets, then verify exact distances. Keep a simple scan for small sets when it benchmarks better. **Validate:** compare results with a brute-force oracle and test shuffled input order. Similarity alone must not authorize automatic deletion.

### 20. Indexing repeats expensive work for unchanged files — P2, confirmed

**Evidence:** [lib.rs:9280](../src-tauri/src/lib.rs#L9280)–9392. Indexing regenerates name embeddings and decodes images for hashes/classification without first excluding unchanged source fingerprints. Image-description embeddings can be submitted as one large collected batch, unlike the bounded filename batches.

**Fix plan:** track source identity, size, high-resolution modification time, and relevant model/preprocessing version. Queue only dirty work, deduplicate in-flight jobs, share image decoding where possible, and bound batches by memory/tokens as well as item count. Model fingerprint invalidation already exists at [lib.rs:9118](../src-tauri/src/lib.rs#L9118); extend that mechanism rather than replace it. **Validate:** a second unchanged scan does no inference or image decoding; one edited image invalidates only its dependent artifacts.

### 21. Every deep query starts several providers, including a live scan — P2, performance target

**Evidence:** [lib.rs:20004](../src-tauri/src/lib.rs#L20004)–20054. A search starts coordinator/provider threads for the index, Windows Search, and a live traversal. Debouncing exists, but each launched query can still perform redundant work; cancellation does not cover every provider's internal work.

**Fix plan:** choose providers from query capabilities, scope coverage, freshness, and measured cost. Use indexed results first only where completeness is known; schedule live fallback for missing coverage. Use a bounded pool, cancellable traversal/database work, and discard obsolete generations. **Validate:** both result completeness and work performed during rapid typing; measure cancelled work that continues running.

### 22. Semantic ranking is limited by an arbitrary 8,000-vector sample — P2, confirmed/performance

**Evidence:** [lib.rs:9418](../src-tauri/src/lib.rs#L9418), 9452. Queries use LIMIT 8000 without an ordering contract, load vectors into maps, and compute similarity after retrieval. Relevant vectors outside that sample cannot influence ranking.

**Fix plan:** for reranking, fetch vectors for actual candidate IDs. For semantic retrieval, use a defined complete scope and normalized exact top-k as the correctness baseline; consider approximate-nearest-neighbor indexing only when corpus size and measurements justify it. Explain retrieval versus reranking in the product behavior. **Validate:** place relevant items beyond the old limit and compare recall, latency, and memory with the exact baseline.

### 23. Thumbnail cache operations amplify database work — P2, performance target

**Evidence:** [lib.rs:7927](../src-tauri/src/lib.rs#L7927), 7948, 7988, 7992, 8991, 9080. Thumbnail reads/writes open connections; reads update access times; inserts can trigger whole-cache size aggregation and pruning. Connection setup also performs schema/migration-related work and configures a sizeable cache.

**Fix plan:** migrate once, use a small connection pool or dedicated cache worker, batch access updates, maintain transactional byte counters, and evict between high/low watermarks instead of recalculating after every insert. **Validate:** cache correctness after crashes plus database statements, lock wait, bytes written, and thumbnail throughput under scrolling.

### 24. In-memory thumbnails can remain stale and evict useful entries — P2, confirmed/risk

**Evidence:** [lib.rs:16058](../src-tauri/src/lib.rs#L16058), 16502, 2556. The memory cache is keyed by path and skips existing entries; worker results lack a complete source-version/generation identity. Memory eviction takes arbitrary keys. General invalidation does not consistently invalidate this cache.

**Fix plan:** version keys by source fingerprint, reject obsolete worker results, and use a byte-budgeted LRU with visible items pinned briefly. Invalidate on watcher/operation events. **Validate:** replace an image at the same path while its thumbnail is loading; scroll away/back and switch directories during generation.

### 25. UI updates rebuild more state than the visible change requires — P2, performance target

**Evidence:** [lib.rs:16095](../src-tauri/src/lib.rs#L16095)–16131. Updates walk the visible-files collection, create new FileItem values, and replace the model. Related updates also rebuild navigation/tab state. View virtualization already exists, but it does not remove these upstream allocations and transformations.

**Fix plan:** keep stable models, update changed rows, format expensive fields lazily, and separate file results from navigation chrome. Coalesce streaming changes within a frame budget. **Validate:** allocation counts and UI-thread p95/p99 latency while results stream into a 50,000-item folder; preserve selection and scroll position.

### 26. Moves prewalk directories before attempting a cheap rename — P2, performance target

**Evidence:** [lib.rs:12738](../src-tauri/src/lib.rs#L12738), 12773, 1840. Copy/move wrappers calculate a recursive size before transfer; a same-volume move can therefore traverse a large tree before a filesystem rename. The “quick” size calculation caps files at 25,000, so totals are approximate and directory traversal can still be substantial. Large fs::copy calls provide no intermediate progress.

**Fix plan:** validate the operation, then try an eligible rename before enumerating copy work. For actual transfer, build a reusable plan with progressive/explicitly estimated totals and chunked or native progress-aware copying. **Validate:** same-volume directory moves issue no full prewalk; cross-volume totals and large-file progress remain truthful.

### 27. Cancellation, pause, and queue completion have inconsistent semantics — P1/P2, confirmed

**Evidence:** [lib.rs:7318](../src-tauri/src/lib.rs#L7318), 7396, 7511, 12773. ZIP extraction/copy loops do not consistently observe cancellation or pause; external 7z waits do not expose a cancellable child lifecycle. Large fs::copy calls only check around the call. Some fallible paths exit after queue start without a corresponding completion update. ZIP totals use compressed archive bytes while progress adds extracted bytes.

**Fix plan:** a shared operation context with cancellation/pause checkpoints, progress units, and a guard ensuring exactly one terminal outcome. Acknowledge cancellation only when work stops; terminate child processes through owned handles and clean only owned staging files. **Validate:** cancel/pause each operation phase, inject read/write failures, and assert queue completion plus bounded stop latency. Show estimated/unknown totals honestly.

### 28. A conflict prompt can lose the rest of a paste batch — P2, confirmed

**Evidence:** [lib.rs:22913](../src-tauri/src/lib.rs#L22913)–22949 and 22253. Preflight returns after storing a single conflicting source/destination/cut choice. Resolving ConflictPaste applies that one decision without retaining a batch cursor and continuation for the remaining items.

**Fix plan:** retain a complete operation plan, current position, and conflict decisions. Resume from the same plan after each answer; support apply-to-all policies explicitly. **Validate:** conflicts at the first, middle, and last item, including skip, rename, replace, cancel, and mixed file/directory batches.

### 29. Text comparison can block, hide read errors, and misalign changes — P2, confirmed

**Evidence:** [lib.rs:26373](../src-tauri/src/lib.rs#L26373)–26410. The callback reads entire files before checking its display-size limit, maps read errors to empty text, and compares matching line positions with a first-400-line cap. A single insertion makes subsequent lines appear changed. It also shares the secondary-pane selection defect in finding 2.

**Fix plan:** bounded worker reads with explicit encoding/error states; use Myers or patience diff with size/time limits and cancellation. Distinguish truncation from full comparison. **Validate:** one-line insertion, moved blocks, unreadable files, binary/invalid text, large files, and selections from either pane.

### 30. Some document/image limits apply after expensive allocation — P1/P2, risk

**Evidence:** [lib.rs:2866](../src-tauri/src/lib.rs#L2866)–2877 reads OpenXML entries into strings before applying the combined text cap. A small compressed input can expand substantially. The PDF helper at [lib.rs:2144](../src-tauri/src/lib.rs#L2144) reads before its own size check, even though some callers may impose earlier limits. [inference.rs:588](../src-tauri/src/inference.rs#L588) decodes an image before shrinking it. Ordinary text preview already uses a bounded read at [lib.rs:5246](../src-tauri/src/lib.rs#L5246).

**Fix plan:** enforce compressed and expanded-byte limits, per-entry/whole-document budgets, image dimension/pixel limits, and time/cancellation budgets before or during allocation. Report skipped/truncated inputs. **Validate:** disposable high-expansion archives, oversized image dimensions, malformed documents, and slow storage; measure peak memory and cancellation latency.

## Local AI and asset lifecycle

### 31. The quality image classifier uses the wrong model contract — P1, confirmed against primary documentation

**Evidence:** [inference.rs:588](../src-tauri/src/inference.rs#L588)–623 constructs a channels-first NCHW tensor with ImageNet normalization for all classifiers. The bundled EfficientNet-Lite4 model instead expects NHWC [1,224,224,3] and different pixel normalization. Its Softmax:0 output is already normalized; [inference.rs:655](../src-tauri/src/inference.rs#L655)–660 and 691–693 apply softmax again. These requirements are documented by the [ONNX model maintainers](https://github.com/onnx/models/blob/main/validated/vision/classification/efficientnet-lite4/README.md).

**Impact:** the quality profile has an input-shape mismatch; fixing only that still leaves incorrect preprocessing/output handling. Applying softmax again to a 1,000-class probability vector reduces even an extreme winner to about 0.0027, below the code's 0.08 threshold.

**Fix plan:** model-specific tensor layout, resize/crop, normalization, output names/types, and labels in validated metadata. Validate a known image after installation and before activation. **Validate:** shape and reference-output tests for every shipped profile, including confidence thresholds; avoid treating successful session construction as successful inference.

### 32. Hardware acceleration can be reported despite CPU fallback — P2, confirmed failure mode

**Evidence:** [inference.rs:141](../src-tauri/src/inference.rs#L141)–215 builds provider candidates without requiring registration errors, adds CPU fallback, and labels the first successfully created session with the requested candidate. The pinned ort rc.12 source defaults to silent provider-registration failure; the public [ExecutionProviderDispatch documentation](https://docs.rs/ort/latest/ort/ep/struct.ExecutionProviderDispatch.html) describes that fallback behavior. [lib.rs:5423](../src-tauri/src/lib.rs#L5423) also infers a compute label from hardware presence before a selected provider is known.

**Fix plan:** require registration success when probing candidates, run a real inference probe, and report observed provider assignment or a qualified mixed/unknown state. Hardware detection alone is not evidence of model execution on that device. **Validate:** unavailable/broken GPU or NPU providers, unsupported operators, mixed execution, and CPU-only installations. Compare end-to-end throughput before selecting a preferred backend.

### 33. AI asset updates can destroy a working installation before replacement succeeds — P1, confirmed

**Evidence:** [local_ai.rs:543](../src-tauri/src/local_ai.rs#L543)–549 deletes an existing destination before downloading. The installation loop around line 704 updates related assets individually. A later failure can leave a mixed set of models/tokenizers; the soft-failure path around line 938 infers preservation from file presence rather than a validated coherent installation.

**Fix plan:** stage a complete versioned asset set, verify checksums/contracts and smoke-test it, then atomically activate a manifest pointer. Keep the previous set for rollback; coordinate activation with in-flight sessions. **Validate:** connection loss and corrupted downloads at every asset boundary, insufficient disk space, and failed inference after download. The previously active profile must remain usable.

### 34. ONNX runtime validation relies on file presence — P2, confirmed

**Evidence:** [local_ai.rs:341](../src-tauri/src/local_ai.rs#L341), 506. Runtime handling bypasses the usual asset verification and accepts an existing runtime DLL as installed. An obsolete or corrupted DLL can survive repair/update checks.

**Fix plan:** verify the extracted runtime version and hashes, stage a coherent runtime bundle, and handle locked DLLs through activation at the next launch when necessary. **Validate:** wrong-version, truncated, missing companion, and in-use DLL cases; the displayed revision must match what actually loads.

### 35. AI catalog validation and installation locking are incomplete — P2, confirmed/risk

**Evidence:** [local_ai.rs:281](../src-tauri/src/local_ai.rs#L281) accepts schema versions broadly and only lightly checks catalog structure. Profile resolution around line 295 can panic on an empty profiles map. Asset paths around line 502 directly join catalog filenames. Installation locking around line 454 checks existence then writes a lock non-atomically; some early-return paths can bypass cleanup, and age-based stale detection is not proof that the owner stopped.

**Fix plan:** validate supported schema versions, nonempty profiles, every referenced asset, model contracts, safe filenames, download origins, and hashes before accepting a catalog. Use atomic lock creation or an OS lock with an RAII owner; verify owner liveness before stale recovery. **Validate:** malformed/future catalogs, absent profile references, unsafe filenames, concurrent installations, crashes, and installs lasting beyond the stale threshold. No unsafe catalog was exercised against real user files.

### 36. Changing an AI profile can bypass the network preference — P2, confirmed

**Evidence:** [lib.rs:27750](../src-tauri/src/lib.rs#L27750) lacks the network-enabled gate used by other AI install/repair/update actions. The profile control around [main.slint:9560](../src-tauri/ui/main.slint#L9560) is not consistently disabled for network-off/busy state. A busy guard can reject work after the requested preference has already changed.

**Fix plan:** enforce network and operation-state policy in one service used by all entry points. Keep requested and installed/active profile states separate; activate a preference only when its required assets are ready. **Validate:** change profiles while offline, during another install, and after a failed download; labels and actual active models must agree.

### 37. AI status polling can block and override preferences — P2, confirmed/performance

**Evidence:** [lib.rs:15073](../src-tauri/src/lib.rs#L15073) and 28579 refresh status, manifest, and disk-usage information repeatedly while relevant UI/status states are active. [lib.rs:28594](../src-tauri/src/lib.rs#L28594) resets sessions on the UI path and can wait on inference locks. Installed-state handling around 28606/28610 re-enables semantic search/image descriptions, including after updates or repairs when users may have disabled them.

**Fix plan:** publish a versioned worker-side status snapshot, update the UI only when it changes, and retire/reset sessions off the UI thread after in-flight work releases them. Preserve explicit preferences; first-install defaults must be distinguishable from repair/update completion. **Validate:** repair with features disabled, finish an update during inference, and inspect idle/settings CPU and input latency.

## UI, Windows integration, and release quality

### 38. Closing a preceding tab can activate the wrong tab — P2, confirmed

**Evidence:** [lib.rs:20164](../src-tauri/src/lib.rs#L20164) removes a tab and clamps the active index without consistently decrementing it when the removed tab was before the active one. With A/B/C/D and B active, closing A can move focus to C.

**Fix plan:** store active tab identity independently of position, or adjust indices according to removal position before restoring view state. **Validate:** close every tab relative to the active one; preserve the intended path, selection, scroll, and history.

### 39. Shortcut editing permits ambiguous or unreachable bindings — P2, confirmed/UX

**Evidence:** [shortcuts.rs:213](../src-tauri/src/shortcuts.rs#L213) resolves duplicate bindings through sorted command iteration instead of rejecting ambiguity. Capture at [lib.rs:21621](../src-tauri/src/lib.rs#L21621) does not fully validate conflicts. Formatting around [shortcuts.rs:124](../src-tauri/src/shortcuts.rs#L124) can omit Shift for implied punctuation, while the display string is persisted around [lib.rs:21654](../src-tauri/src/lib.rs#L21654). [main.slint:11010](../src-tauri/ui/main.slint#L11010) intercepts navigation/reserved keys before general capture.

**Fix plan:** persist structured key/modifier chords separately from display text, precompile a lookup map, reject/report conflicts, and document reserved keys. Route capture before normal actions while the editor owns focus. **Validate:** punctuation, Shift combinations, supported keyboard layouts, duplicate assignments, reserved keys, and save/restart round trips.

### 40. Custom controls lack explicit accessibility semantics — P2, UX gap

**Evidence:** the shared ToolButton at [main.slint:348](../src-tauri/ui/main.slint#L348) uses Rectangle/TouchArea without explicit semantic role/name or a complete keyboard-focus activation contract. No explicit accessible-* properties were found in the main UI file. This is a source-level gap, not a completed screen-reader compatibility test; built-in controls can still provide default semantics.

**Fix plan:** give reusable custom controls accessible names/roles, visible focus, keyboard activation, and appropriate state announcements. Cover icon-only controls, pane changes, search progress, selection counts, and operation results. **Validate:** Narrator, keyboard-only operation, high contrast, reduced motion, and DPI scaling in both pane/view modes.

### 41. Search help still has sizing, translation, and usefulness gaps — P2/P3, confirmed/UX risk

**Evidence:** the revised panel around [main.slint:5116](../src-tauri/ui/main.slint#L5116) uses a fixed 344-pixel height and a capped width; example-description space is narrow and can elide useful explanations. Examples are not directly selectable/copyable actions. The newly introduced help strings were absent from the Italian/Spanish translations when searched. Its usefulness also depends on fixing query behavior in finding 11.

**Product judgment:** retain help only as an explanation of what the search box adds: scope, supported compound queries, provider coverage, and examples that can be inserted and edited. Repeating filter/tag chips adds little value. The earlier change removed the duplicate chip controls; this audit proposes further work only.

**Fix plan:** use content-aware layout with a bounded scroll area, keyboard-accessible “use example” actions, complete translations, and truthful syntax/scope guidance. Ordinary current-folder filters should stay in the filter UI. **Validate:** minimum window size, 100–200% scaling, long translated labels, keyboard focus, and every example's actual result semantics.

### 42. Shell menu invocation may reuse stale numeric command IDs — P2, risk

**Evidence:** [windows_integration.rs:242](../src-tauri/src/windows_integration.rs#L242) builds a menu in a context that is later released; invocation at line 283 recreates shell context and uses a previous numeric offset. Dynamic extensions need not assign identical offsets on each construction. Menu tracking around line 303 does not show full IContextMenu2/3 message forwarding. COM initialization around line 215 also needs a balanced lifetime audit.

**Fix plan:** keep the menu and owning shell context alive through invocation, or resolve and validate a stable canonical verb where supported. Forward extension menu messages and use a balanced COM lifetime guard. **Validate:** dynamic/owner-drawn extensions, nested menus, selection changes, cancelled menus, and repeated invocations. No wrong third-party action was reproduced during this static audit.

### 43. Update selection, verification, and completion need stronger contracts — P2, known gap/risk

**Evidence:** [lib.rs:10224](../src-tauri/src/lib.rs#L10224) chooses an executable, then MSI, without a strong architecture/product asset contract. Verification around [lib.rs:10708](../src-tauri/src/lib.rs#L10708) checks a digest only when one is available; otherwise size is the main additional check. Installer failure is logged without a durable completion receipt clearly reflected in the app. Release/signing documentation already acknowledges signing gaps.

**Fix plan:** select an explicit product/architecture asset, require a verified release digest before execution, validate the publisher when signed, and record install outcome for the next launch. Treat signing as a release-pipeline task, not a UI label. **Validate:** wrong architecture, missing/bad digest, truncated download, installer rejection/failure, and relaunch after failed update. This is not evidence of a compromised release.

## Architecture and test coverage

### 44. Architecture and tests do not protect the most important invariants — P2, maintainability/test gap

**Evidence:** lib.rs contains 31,409 lines spanning state, operations, search, indexing, UI callbacks, and installation. The source scan found 55 test annotations, largely around isolated helpers; this review did not establish end-to-end coverage of selection identity, replay history, conflicting batches, or partial-index reconciliation. Passing cargo check and Clippy does not test those behaviors.

**Fix plan:** first add regression tests around the confirmed defects, then extract cohesive boundaries: operation engine/history, query planning/predicates, index writer, pane state, preview pipeline, asset manager, persistence, and background scheduling. Keep behavior changes small and reviewable. Avoid a wholesale rewrite or file splitting without clearer ownership/contracts. **Validate:** the invariant-focused suite below, with small fixtures that fail on the current defect and succeed on the intended behavior.

## Better targeting and algorithms: where to spend effort

These changes are candidates for measured improvement, not promised speedup percentages. Prioritize avoiding unnecessary work before introducing more parallelism or a more complex index.

| Area | Current cost/problem | Preferred approach | Measure or correctness gate |
| --- | --- | --- | --- |
| Selection | Position-based identity changes under sorting | Stable entry identity and explicit pane ownership | Selected paths remain unchanged through reorder |
| Indexing | Partial batches reconcile as complete snapshots | Incremental upsert plus completed-scan reconciliation | Exact coverage; no unrelated row deletion |
| Search | Overlapping providers scan broadly per query | Capability/coverage-aware planner and shared predicate | Oracle parity, first/complete result latency, bytes read |
| Derived AI/image data | Recompute unchanged inputs | Versioned fingerprints, dirty queue, shared decode | Inference/decode counts on unchanged scans |
| Semantic ranking | Broad vector load with arbitrary cap | Candidate-ID fetch or measured retrieval index | Recall versus complete exact baseline, memory |
| Similar images | All-pairs Hamming comparisons | BK-tree/multi-index candidates plus exact verification | Oracle parity, order semantics, comparisons |
| Storage | Always follows totals with duplicate hashing | Optional phase; reuse size buckets | Extra reads avoided; cancellation latency |
| Thumbnail cache | Connection/write/prune work per item | Dedicated worker/pool, batched touches, byte counters | DB statements/write volume and cache hit rate |
| UI model | Rebuild full collections on incremental change | Stable model, row deltas, bounded update batches | UI p95/p99 latency and allocations |
| Transfers | Prewalk before rename; repeated traversal | Validated reusable plan; rename fast path | Metadata calls, bytes read, progress accuracy |
| Text diff | Same-index comparisons | Bounded Myers/patience diff | Correct edit alignment, time/memory budget |
| Background jobs | Independent jobs duplicate or outlive demand | Bounded priority queues, generation cancellation | Queue depth, obsolete work, visible-item latency |

For small collections, linear scans can outperform an additional index. Choose thresholds from representative measurements. For correctness-sensitive search and similarity changes, retain a simple reference implementation as a test oracle.

## Recommended implementation sequence

1. **Protect file identity and recoverability:** findings 1–10, 27, and 28. Establish selection, containment, replace, cancellation, persistence, and undo/redo invariants before making operations faster. The file-operation engine is the first shared boundary to create.
2. **Make search results trustworthy:** findings 11–16. Define query semantics and source scope once; fix index reconciliation before relying on coverage-based search planning. Make every displayed help example pass the same query oracle.
3. **Measure and remove wasted work:** findings 17–26 and 30. Add lightweight instrumentation, move blocking jobs off the UI thread, impose resource budgets, then tune incremental processing and caches. Resolve the AI contract in finding 31 before collecting inference-performance baselines.
4. **Make AI installation and execution reliable:** findings 31–37. Validate each model contract, update assets transactionally, report actual execution, and preserve preferences/offline policy.
5. **Finish interaction and integration quality:** findings 38–43. Tab/shortcut behavior, accessibility, search help, shell menus, and update outcomes each need focused validation. Escalate release/update trust work earlier if a release is imminent.
6. **Extract architecture alongside these fixes:** finding 44. Move tested behavior behind small interfaces as each area is repaired; do not defer all testing until a later refactor.

These are dependency-based work packages, not time estimates. A narrower first release should fix safety and search correctness before adding any of the larger features below.

## Validation and benchmark plan

All destructive/recovery scenarios should use generated disposable fixtures and explicit temporary roots. Do not run them against the user's working folders.

### Correctness and failure-injection suites

- **Operation matrix:** files/directories; same/cross-volume; duplicate names; conflicts at each batch position; locked/read-only destinations; permission failures; disk-full simulations; cancel/pause at each phase; UNC and alias paths. Assert that source/destination content and operation history agree after every outcome.
- **Undo/redo state machine:** interleave new actions with undo/redo, partial failures, external file edits, and batch operations. Each successful action has one reversible record; replay does not create extra history; a new action invalidates the redo branch; recycle semantics persist.
- **Selection/pane identity:** sorting, filtering, async inserts/removals, tab changes, and pane switches retain only the intended identities. Every command resolves paths from the active pane through the same API.
- **Search oracle:** run each supported query against a small explicit expected result set. Compare every provider and merged output. Include tags, phrases, extension/type, size/date boundaries, content, Unicode, scope boundaries, and combined constraints. Exercise cancellation and results arriving out of order.
- **Index consistency:** deep/wide traversal crossing flush thresholds; cancellation/access denial mid-directory; source deletion/rename during scans; concurrent scans. Partial work never authorizes deletion of unrelated index rows.
- **UI/UX:** both panes and all view modes, supported themes/languages, minimum window dimensions, 100/125/150/200% scaling, keyboard-only flow, Narrator, high contrast, and reduced motion. Verify focus, tooltip/label meaning, truncation, progress, and empty/error states.
- **AI/assets:** every profile with known-image/text fixtures; unavailable/failing hardware providers; real selected provider reporting; corrupt/missing assets; interrupted installs; offline mode; concurrent operations; repair/update with features explicitly disabled. Validate old-profile rollback and model fingerprint invalidation.
- **Preview/archive budgets:** malformed documents, high expansion ratios, large image dimensions, unsafe names, and destination junctions. Bound memory and time; preserve extraction containment and explain rejected/skipped entries.
- **Persistence/lifecycle:** crash between write stages, immediate shutdown after queued writes, corruption recovery, and simultaneous windows. No silent loss of tags, notes, settings, or history.
- **Windows/release:** dynamic shell extensions, stale menus, registry ownership changes, failed installers, wrong update assets, and uninstall after another file manager takes ownership. Use isolated test environments for registry/install cases.

### Performance corpus and measurements

Use separate cold/warm-cache runs on realistic hardware. A useful corpus spans 1,000/10,000/50,000 entries in a folder; 100,000–1,000,000 files across deep and wide trees; 10,000 mixed-size images with both duplicate and unique content; and a mix of local SSD, HDD, network, and cloud-placeholder paths. Start smaller when the hardware cannot safely support those sizes.

Record UI-event-loop p50/p95/p99 latency, time to first and complete search results, cancellation acknowledgement and actual stop time, queue depth and obsolete work, filesystem metadata calls/bytes read, database statements/lock waits, inference/decode counts, peak RAM/VRAM, cache hit rate, and idle/minimized CPU. Record environment, corpus, model profile, and cache state alongside each run.

Establish baselines before setting numerical acceptance targets. This audit did not collect runtime performance measurements; operation counts and complexity observations are not measured speedups.

## Three substantial feature proposals

### 1. Reviewable folder synchronization and versioned backup

**User value:** keep two locations aligned while understanding exactly what will change and retaining a path back from mistakes. Existing dual-pane comparison is a useful starting point; a reliable sync plan and version history would add a distinct capability.

**First scope:** one-way synchronization with a preview of copies, updates, conflicts, and optional deletions; exclusion rules; dry-run summaries; preserved replaced/deleted versions; and a final outcome report. Keep deletion off by default for a newly configured job. Two-way synchronization should follow only after storing a common baseline, so independent edits can be recognized as conflicts.

**Targeting/algorithm:** compare indexed metadata first; hash only ambiguous or changed candidates; retain fingerprints and directory summaries between runs; build a dependency-ordered operation plan. For two-way sync, use a three-way comparison against the prior successful baseline rather than interpreting every difference as a replacement.

**Prerequisites and acceptance:** the safe operation engine, stable identity, transactional replacement, and durable history from the audit. Re-running an unchanged job performs no transfers; interruption never silently destroys the only copy; conflicting edits are presented explicitly; each deletion/replacement follows the reviewed plan.

### 2. Incremental document-content search with optional local OCR

**User value:** find a document by what it says, see why it matched, and narrow it with reliable date/type/tag filters. The app already has name embeddings and live content extraction; persistent content indexing, useful snippets, and optional OCR would extend those into a cohesive feature.

**First scope:** opt-in folder coverage, a bounded background extractor, incremental full-text indexing for supported text/document types, highlighted snippets, exact scope/coverage status, and saved queries that stay current. Add OCR for selected scanned PDFs/images as a separate opt-in stage with clear resource controls.

**Targeting/algorithm:** source fingerprints invalidate only changed documents; bounded text chunks feed FTS; metadata predicates narrow candidates before expensive work. Store match offsets for snippets, and use embeddings only for an explicitly supported semantic mode. OCR work has its own low-priority queue, page/pixel budgets, and cancellation.

**Prerequisites and acceptance:** unified query semantics, correct scope and reconciliation, resource limits, and validated model contracts. Exact queries match a reference corpus; snippets point to actual text; excluded folders are not indexed; unchanged rescans do no extraction; users can see and remove indexed content.

### 3. Durable transfer and recovery center

**User value:** recover interrupted large operations, understand partial outcomes, and safely retry only what remains. The app already has an operation queue; persistence, checkpoints, verified resume, and recovery guidance would make this a substantial extension.

**First scope:** persist operation plans and per-item outcomes; show what completed, failed, or remains after restart; retry failed items; preserve replacement backups; and support resumable large-file copying where source/destination validation permits it. Destructive steps must be revalidated after restart rather than resumed blindly.

**Targeting/algorithm:** a journaled state machine, stable source fingerprints, owned staging files, byte checkpoints with integrity verification, and bounded scheduling per storage device. Resume only when the current source and checkpointed data match; otherwise restart that item or request a new decision. Commit completed files atomically where supported.

**Prerequisites and acceptance:** undo/redo and queue-state fixes, transactional persistence, containment, replacement staging, and consistent cancellation. Kill/restart at every transfer phase; completed files remain valid, incomplete files stay clearly staged, and retry never silently overwrites a changed target.

**Recommended order:** build the durable operation/recovery foundation first, then synchronization. Content search can proceed as a separate stream once query correctness and indexing integrity are fixed. These proposals are plans only; none was implemented in this audit.
